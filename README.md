# みにかぼ MSノート

多発性硬化症（MS）に関する記録を、**みにかぼ本人の iPhone の中だけ**で管理するための個人用 PWA です。

> **このアプリは個人の記録を目的としており、診断や治療判断を行うものではありません。
> 急激または強い症状がある場合は、アプリの表示を待たず医療機関へ相談してください。**

---

## 1. アプリの目的

次の内容を継続的に記録・確認します。

- 投薬予定と投薬履歴（実施・延期・見送り）
- 週1回の簡単な体調確認
- 新しい症状、既存症状の悪化と、その日ごとの経過
- 再発後・治療後などの「観察モード」（期間を決めて毎日記録）
- 診察、MRI、血液検査、髄液検査、ステロイドパルスなどの医療履歴（添付ファイル付き）
- EDSS、T25FW、9HPT、SDMT、BICAMS などの**測定結果の記録**
- 診察時に医師へ質問したい内容
- 診察用レポート（印刷 / PDF 保存）

### 行わないこと（安全設計）

- 再発・PIRA・副作用の**自動診断をしません**
- 薬の量や投与日程を**医学的に提案しません**（すべて本人が入力します）
- 投薬予定日を過ぎても「今すぐ投与してください」などの**医療指示を出しません**
- 薬の中止・再開を勧めません
- 検査結果を正常・異常と**自動判定しません**
- EDSS・SDMT などの**検査そのものは実装していません**（結果の記録のみ）
- AI による診断・予測・治療助言・要約を行いません
- アプリだけで緊急性を否定することはありません

「症状の変化が24時間以上続いている」「複数回の記録で低下傾向がある」といった表示は、
記録された事実に基づく**中立的な案内**であり、診断ではありません。

## 2. 技術構成

| 項目 | 採用したもの |
| --- | --- |
| UI | React 19 + TypeScript |
| ビルド | Vite 6 |
| ルーティング | react-router-dom 7（`HashRouter`） |
| ローカル DB | IndexedDB（Dexie 4） |
| 入力検証 | Zod 3 |
| PWA / SW | vite-plugin-pwa（Workbox `generateSW`） |
| 単体テスト | Vitest 3 + fake-indexeddb |
| E2E | Playwright（iPhone 13 相当のビューポート） |
| スタイル | プレーン CSS（`src/styles/global.css`）。CSS 変数でライト/ダーク対応 |
| フォント | 端末のシステムフォントのみ（リモートフォント不使用） |
| 暗号化 | Web Crypto API（PBKDF2-SHA-256 + AES-GCM） |
| グラフ | 自前の SVG 折れ線グラフ（外部チャートライブラリ不使用） |

**外部通信は一切ありません。** 外部 API・AI API・外部 CDN・外部フォント・アクセス解析・広告・
トラッキング・エラー収集（Sentry 等）を含みません。ESLint ルールで `fetch` / `sendBeacon` の
直接利用も禁止しています。

### アプリ名の変更

アプリ名は **`src/config/appConfig.ts` の 1 か所** だけで管理しています。
`APP_NAME` / `APP_SHORT_NAME` / `APP_ID` を書き換えると、画面タイトル・Web App Manifest・
レポートの見出し・バックアップファイル名・IndexedDB 名がすべて追従します。

### テストの内容

**単体テスト（`src/**/*.test.ts`）**

- 投薬予定の生成（N日ごと / N週間ごと / 個別日付 / 終了日 / 無効化）
- 個別日付と繰り返し予定の併用（導入期＋維持期）
- 予定ルールを変更しても過去の実施履歴が変わらないこと
- 投薬予定日超過（overdue）の判定
- 週次チェックの保存（同一週は 1 件にまとまる、範囲外の値は拒否）
- 症状イベントと日ごとの経過記録
- 暗号化バックアップの作成と復号、平文が残らないこと
- 間違ったパスワード・改ざん・破損ファイルで復元できないこと
- 破損データの復元を試みても既存データが壊れないこと
- IndexedDB のマイグレーション（v1 → v2）
- 日付ユーティリティ、24時間継続判定、低下傾向の判定

**E2E テスト（`e2e/`）**

- 初回起動から 4 タブすべてへの移動
- 外部通信が 1 件も発生しないこと
- 通知・権限 API を呼ばないこと
- コンソールエラーが出ないこと
- 週次チェック / 投薬 / 症状記録の主要フロー
- オフラインでの起動・記録追加・再読み込み後のデータ保持
- オフラインでのバックアップ作成 → 全データ削除 → 復元
- タップ領域 44px 以上、横スクロールが出ないこと
- キーボード操作でのナビゲーション
- Web App Manifest と Service Worker（プリキャッシュ内容）の検証

## 6. GitHub Pages への公開

公開URL: **https://minikabo3901-collab.github.io/minikabo-ms-note/**

`main` ブランチへ push すると `.github/workflows/deploy.yml` が動き、
型チェック → Lint → 単体テスト → 本番ビルド → base 一致の確認 → E2E テスト（オフライン起動と

どれかが失敗した場合はデプロイされません。

### 更新の手順

```bash
git add -A
git commit -m "変更内容"
git push
```

push から 3〜5 分ほどで公開サイトへ反映されます。進行状況は GitHub の **Actions** タブで確認できます。

### 初めて公開する場合（別アカウントで作り直すとき）

1. GitHub で新しいリポジトリを作成します（例: `minikabo-ms-note`）。
2. リポジトリ名がそのまま URL のサブディレクトリになります。
   別名にする場合は `vite.config.ts` の `BASE_PATH` の既定値も合わせてください
   （GitHub Actions 経由なら自動で決まるため変更は不要です）。
3. このプロジェクトを `main` ブランチとして push します。
4. GitHub の画面で次を設定します。

   ```text
   Settings → Pages → Build and deployment → Source → GitHub Actions
   ```

5. 設定後、`main` への push で自動的にビルドと公開が行われます。

### 公開されるもの・されないもの

| 公開される | 公開されない |
| --- | --- |
| アプリのソースコード | あなたが入力した健康記録 |
| ビルドされた HTML / CSS / JS / アイコン | `.msbackup` バックアップファイル |
| README などのドキュメント | IndexedDB の中身 |

入力したデータは GitHub へ送信されず、**iPhone の中の IndexedDB にだけ**保存されます。

## 8. データの保存について

- 記録はすべて**この端末の IndexedDB だけ**に保存されます。
- サーバー送信・クラウド同期・アカウント登録はありません。
- 添付ファイル（JPEG / PNG / PDF）は Blob として IndexedDB に保存します（Cache Storage には保存しません）。
- ページ再読み込み、アプリ終了、オフライン、アプリ更新のいずれでもデータは保持されます。

### データが消える可能性

次の場合、記録は失われます。**復元にはバックアップファイルが必要です。**

- ホーム画面からアプリを削除した場合
- Safari の「履歴と Web サイトデータを消去」を実行した場合
- iOS が長期間未使用のサイトデータを自動削除した場合
- 端末の初期化・機種変更（データは端末間で同期されません）

初回起動時に、ユーザー操作を起点として `navigator.storage.persist()` による永続保存を要求します。
ただしこれは**保証ではなく要求**で、ブラウザが拒否することもあります。
設定画面に現在の状態を表示し、常にバックアップの必要性を案内しています。

## 9. バックアップ方法

1. 右上の歯車から「設定」を開きます。
2. 「データ管理」の「**バックアップ作成**」をタップします。
3. パスワード（8文字以上）を 2 回入力します。
4. 「ファイルを書き出す」でファイルを保存します（iPhone では「ファイル」アプリなどに保存できます）。

- ファイル名: `minikabo-ms-note-YYYYMMDD-HHMM.msbackup`
- 添付ファイルも含まれます。
- **オフラインでも作成できます。**

### バックアップの形式

```jsonc
{
  "format": "minikabo-ms-note-backup",
  "formatVersion": 1,
  "app": "みにかぼ MSノート",
  "createdAt": "2025-06-18T12:34:56.000Z",
  "kdf":    { "name": "PBKDF2", "hash": "SHA-256", "iterations": 310000, "salt": "<base64>" },
  "cipher": { "name": "AES-GCM", "iv": "<base64>" },
  "payload": "<base64: 暗号化された全データ>"
}
```

- 鍵導出: PBKDF2-SHA-256（310,000 回、毎回ランダムな salt）
- 暗号化: AES-GCM 256bit（毎回ランダムな IV）
- **健康データはすべて暗号化された `payload` の中にのみ存在します。**
  ヘッダには形式情報と作成日時しか含まれません。
- **パスワードはアプリに保存されません。忘れた場合、そのバックアップを復元する方法はありません。**

## 10. 復元方法

1. 「設定」→「データ管理」→「バックアップから復元」。
2. `.msbackup` ファイルを選びます。
3. バックアップ作成時のパスワードを入力し、「内容を確認する」をタップします。
4. **作成日時と各データの件数**が表示されます。内容を確認してから「復元する」をタップします。

- 復元は「**現在のデータを置換**」のみです（MVP）。実行前に新しいバックアップの作成を案内します。
- ファイル形式は読み込み時に検証し、復号後の内容も Zod で全件検証します。
- 復元は 1 つの IndexedDB トランザクションで実行され、途中で失敗した場合は
  **ロールバックして元のデータが維持されます**。
- 不正・破損したファイルでは、DB に触れる前に処理を中止します。
- **オフラインでも復元できます。**

## 12. データベース構造

IndexedDB のデータベース名は `minikabo-ms-note`（`APP_ID`）です。定義は `src/db/db.ts`、
型と検証ルールは `src/db/types.ts` にあります。

| テーブル | 内容 | 主なインデックス |
| --- | --- | --- |
| `medications` | 薬（薬名・1回量・単位・投与方法・開始日・終了日・状態・メモ） | `id, name, status, startDate` |
| `scheduleRules` | 投薬予定ルール（個別日付 / N日ごと / N週間ごと） | `id, medicationId, kind, startDate, active` |
| `doseRecords` | 投薬記録（予定 / 実施済み / 延期 / 見送り、部位、反応） | `id, medicationId, scheduledDate, status, [medicationId+scheduledDate]` |
| `weeklyChecks` | 週1回のチェック（0〜4 の5項目、状況フラグ、メモ） | `id, weekStart, recordedDate` |
| `symptomEvents` | 症状イベント（新規/悪化、分類、部位、強さ、影響、状況） | `id, status, onsetAt, kind` |
| `symptomLogs` | 症状の日ごとの経過記録 | `id, eventId, date, [eventId+date]` |
| `observationPeriods` | 観察モードの期間 | `id, status, startDate, endDate, symptomEventId` |
| `observationEntries` | 観察モードの日ごとの記録 | `id, periodId, date, [periodId+date]` |
| `medicalEvents` | 医療履歴（診察・MRI・血液検査・治療など） | `id, date, type` |
| `attachments` | 添付ファイル（Blob 本体、JPEG/PNG/PDF） | `id, createdAt` |
| `measurements` | 測定結果（EDSS・T25FW・9HPT・SDMT・BICAMS など） | `id, date, name` |
| `questions` | 医師への質問メモ | `id, asked, createdAt` |
| `appointments` | 次回診察・検査の予定（アプリ内のみ） | `id, date, done` |
| `meta` | アプリの状態（免責への同意日時、最終バックアップ日時など） | `key` |

全レコードが共通で `id` / `createdAt` / `updatedAt` を持ちます。日付は `YYYY-MM-DD`、
日時は ISO 8601 文字列で保存します（タイムゾーンによる日付ずれを避けるため、
日付計算はすべてローカルタイムの文字列演算で行います）。

### 設計上のポイント

- **投薬予定は DB に保存しません。** ルールから毎回計算します（`src/features/medication/schedule.ts`）。
  実施・延期・見送りだけが `doseRecords` に保存されます。
  この分離により、**予定ルールを変更しても過去の実施履歴は絶対に変化しません**。
  ルール変更は未来の予定の計算結果にだけ反映されます。
- 過去の記録の修正は、投薬記録の画面で明示的に保存操作を行ったときにだけ発生します。
- `deleteAllData()` は記録と添付ファイルをすべて削除しますが、
  医療上の免責への同意記録だけは残します（再度の同意を求めないため）。

## 13. 将来スキーマを変更する方法

`src/db/db.ts` の `MsNoteDb` に、**既存の `version()` ブロックを書き換えずに**新しい
バージョンを追加します。

```ts
// 1. 既存の version(1), version(2) には手を触れない
//
// 2. 新しいバージョンを追加する
this.version(3)
  .stores({
    // 追加・変更するテーブルだけ書く（変更しないテーブルは省略できる）
    newTable: 'id, someIndex',
    // インデックスを追加する場合は、そのテーブルの定義を丸ごと書き直す
    measurements: 'id, date, name, facility',
    // テーブルを削除する場合は null を指定する
    // oldTable: null,
  })
  .upgrade(async (tx) => {
    // 3. 既存レコードの補完（backfill）が必要ならここで行う
    await tx.table('measurements').toCollection().modify((m) => {
      if (m.facility === undefined) m.facility = '';
    });
  });
```

あわせて次を更新してください。

1. `src/db/types.ts` の Zod スキーマ（新しい項目は `.default()` を付けると既存データが通ります）
2. `src/db/db.ts` の `DATA_TABLES`（バックアップ・件数集計の対象）
3. `src/db/repo.ts` のリポジトリ関数と `TABLE_LABELS`
4. `src/features/backup/backup.ts` の `payloadSchema`
5. `src/db/migration.test.ts` にマイグレーションのテストを追加

バックアップの形式を破壊的に変更する場合は `BACKUP_FORMAT_VERSION` を上げ、
`parseEnvelope` に旧バージョンの読み込み処理を追加してください
（新しい形式のファイルを古いアプリで開こうとした場合は、その場でエラーになります）。

## 14. 実装上の判断（仕様に明記が無かった部分）

| 判断 | 理由 |
| --- | --- |
| **PDF は「印刷用レイアウト + ブラウザの PDF 保存」で作る** | 端末の日本語システムフォントがそのまま使われるため文字化けが起きず、PDF 用の日本語フォントを同梱する必要がありません（アプリ容量とフォントライセンスの両面で有利）。iPhone では「印刷」→ 共有 →「ファイルに保存」で PDF になります。オフラインでも動作します。日本語フォントを同梱していないため、ライセンス表記の対象となるフォントはありません。 |
| **ルーティングは `HashRouter`** | ホーム画面に追加した PWA でも、オフラインでも、サーバー側の設定なしに全画面へ遷移できるためです。 |
| **投薬予定はルールから毎回計算（DB に保存しない）** | 「予定ルールの変更が過去の履歴を変えない」という要件を、設計レベルで保証するためです。 |
| **`kind: 'dates'`（個別の日付）は開始日・終了日で絞り込まない** | 入力した日付が黙って消えるのを避けるためです。開始日は入力された最も早い日付を自動で採用します。 |
| **週次チェックは月曜始まりの週で 1 件** | 「週1回」を明確に定義し、同じ週に何度開いても記録が重複しないようにするためです。 |
| **自動保存の対象は「すべての項目が任意」の画面のみ** | 週次チェックの詳細、症状の今日の状態、観察モードの毎日の記録は入力の途中でも壊れないため、変更が止まってから自動保存し、画面遷移時にも書き出します。薬や症状イベントの新規作成など必須項目がある画面は、検証が必要なため明示的な「保存する」操作にしています。 |
| **「3回連続で悪化」の判定** | 同じ項目の値が 3 回連続で前回より悪くなった場合のみ、中立的な案内文を表示します（4 点以上の記録が必要）。診断は行いません。 |
| **添付ファイルの上限は 1 件 8MB** | 端末の保存容量を圧迫しないための安全な上限です。追加前にファイル名とサイズを表示し、確認してから保存します。 |
| **全データ削除は「削除」と入力する二段階確認** | 誤操作による取り返しのつかない削除を防ぐためです。 |
| **バックアップに `meta` テーブルを含めない** | 免責への同意日時や最終バックアップ日時は端末ごとのアプリ状態であり、健康データではないためです。 |
| **E2E は Chromium のモバイルエミュレーション** | Windows 環境でも安定して実行できるためです。実機の iOS Safari での確認は別途行ってください。 |

## 16. 画面構成

下部ナビゲーションは 4 項目のみです。設定は**右上の歯車**から開きます。

| タブ | 内容 |
| --- | --- |
| **ホーム** | 次の投薬 → 今週のチェック（未記録時のみ） → 症状の変化を記録 → 継続中の症状 → 次回診察・検査 |
| **記録** | 週次チェック / 症状 / 投薬管理 / 投薬カレンダー / 観察モード / 医療履歴 / 測定結果 / 次回予定 |
| **経過** | 期間（1か月・3か月・6か月・1年・全期間）と表示項目を切り替えられるグラフとタイムライン |
| **診察** | 質問メモ / 診察用レポート / 次回予定 / 医療履歴 |

連続記録日数、ランキング、スコア競争、記録が途切れたことへの警告など、
罪悪感を生むゲーミフィケーションは実装していません。
